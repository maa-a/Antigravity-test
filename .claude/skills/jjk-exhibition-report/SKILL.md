# 呪術廻戦展 LEGS商品 販売分析レポート

新しい日報や在庫データが届くたびに、**同じ仕様・同じシート構成**でExcelレポートを作り直すための
スキル。仕様は交渉の積み重ねでできているので、都度考え直すより
`references/requirements.md` を読んで踏襲するほうが速く、確実に依頼者の期待に合う。

## 最初にやること

1. **`references/requirements.md` を読む。** 何を出すか・なぜそう出すかが全部書いてある。
   ここを飛ばすと、過去に指摘済みの論点（東京を根拠から除外する、1人あたり売上に正規化する、
   在庫を会場順に引き当てる等）を落としがち。
2. **`scripts/config.py` を開いて、今回の更新で変わる箇所を特定する。**
   よくある更新は下の「更新パターン」を参照。

## 生成手順

依頼者から受け取ったファイルのパスを確認したうえで、3ステップを順に実行する。

```bash
S=.claude/skills/jjk-exhibition-report/scripts
W=$(mktemp -d)

# 1) データ抽出（列レイアウトはヘッダ文字列から自動判定する）
python3 $S/extract_data.py --out $W \
  --venue 東京=<池袋のxlsx> \
  --venue 名古屋=<名古屋のxlsx> \
  --venue 博多=<博多のxlsx> \
  --venue 大阪=<梅田のxlsx> \
  --venue 札幌=<札幌のxlsx> \
  --ledger <在庫フロー台帳のxlsx>

# 2) レポート生成
python3 $S/build_report.py --data $W --out "<出力先>.xlsx"

# 3) 数式の再計算 → フォント復旧（この順序でないと意味がない）
#    recalc.py は xlsx スキル同梱のもの（通常は ~/.claude/skills/xlsx/scripts/recalc.py）
python3 "$(ls ~/.claude/skills/xlsx/scripts/recalc.py /root/.claude/skills/xlsx/scripts/recalc.py 2>/dev/null | head -1)" "<出力先>.xlsx" 780
python3 $S/fix_font.py "<出力先>.xlsx"
```

`recalc.py` は LibreOffice を使うので、`libreoffice-calc` が無い環境では
`apt-get install -y libreoffice-calc` が必要（core だけだと Calc フィルタが無く、
「source file could not be loaded」やタイムアウトになる）。所要は5〜10分程度。

`recalc.py` が `total_errors: 0` を返すまで直す。エラーが残ったまま納品しない。

**`fix_font.py` は必ず recalc の後に走らせる。** LibreOffice は保存時に Meiryo UI を
インストール済みフォントへ置換してしまうため、styles.xml を直接書き戻して復旧している
（openpyxl で開き直すとキャッシュ済みの計算結果が消えるので、この方法をとっている）。

## 検算

納品前に、生成物の数値を Python で独立に計算して突き合わせる。数式の参照ずれは
recalc がエラーを出さないまま静かに間違うので、目視では気づけない。

最低限、次を確認する。

- 各会場の日次合計＝販売数、販売可能数−販売数＝理論在庫（`extract_data.py` が警告を出す）
- ①シートの予測販売数が、モデル定義どおりに再計算した値と一致する
- ③⑧⑪の在庫収支が整合する（実在庫 − 会期予測 ＝ 石川以降の供給可能在庫）
- フォントが全セル Meiryo UI

`references/requirements.md` の末尾に前回の主要数値を載せてある。大きくズレたら
入力データか `config.py` を疑う。

## 更新パターン

### 開催中会場の日報が1日分増えた
`config.py` の `DATA_DAYS[CURRENT]` を実績日数に更新する（`BASE` は自動追従）。
会期倍率gの基準日数が変わるので、全会場のgと予測が動く。サマリーの文言も
「初N日」表記が自動で変わる。

### 会場が終わって次の会場が始まった
`VENUES` に新会場を追加し、`RUN` / `DATA_DAYS` / `PERIOD` / `HALL` / `VENUE_COLOR` を埋める。
`CURRENT` を新会場に変更。`G_WEIGHT` は「直近かつ会期日数と品揃えが近い会場を2倍」の
考え方で置き直す。`FUTURE` から開催済み会場を外す。

### 運営から欠品報告メールが届いた
`SHORTAGE` を書き換え、`SHORTAGE_REPORT_DATE` を更新する。
④シートに「運営 欠品報告」「モデル×現場 突合」列として反映され、
サマリーに見落とし／空振りの件数が出る。**倉庫残がある品目は「追加生産不要・追納で対応可能」と
明示する**のが依頼者の一番知りたいことなので、ここは省略しない。

### 在庫データが更新された
`--ledger` に新しいファイルを渡す。**在庫は必ず「在庫フロー台帳」の最終「実在庫」列から取る。**
同じファイルに池袋終了時点の古いスナップショット（元データ／在庫合算／12月清算後）が同居していて、
そちらを使うと在庫判定が壊れる。`extract_data.py` は採用した列と段階名を必ず表示するので、
最新会場のものになっているか目で確かめる。`config.py` の `STOCK_DATE` も更新。

在庫がフロー計算でマイナスになったら、真っ先にスナップショットの日付を疑う。
過去に実際に取り違えが起き、宿儺の指風お菓子を30倍に過大評価していた。

### 生産日数や会場比率が変わった
`PROD_MONTHS` / `FUTURE` / `VEN_START` / `PLAN_GOODS` を更新する。
東京対比の会場比率は「前提・入力」シートで4シナリオ切替できる作りなので、
新しい前提が来たらシナリオ表（`build_report.py` の `SCN`）に足す。

## 報告のしかた

Excelを渡して終わりにしない。チャットでは次を必ず書く。

- 前回から**変わった数値**を対比表で（何がどう動いたか、なぜ動いたか）
- **意思決定に効く結論**（追加発注が要るか、いつまでに、どの会場向けに、何個）
- **要確認事項**（前提が崩れると結論が変わるもの。`requirements.md` 末尾のリストを毎回見直す）

依頼者は数字を眺めたいのではなく、発注するかどうかを決めたい。
「全体では余っているが、この5品目だけこの期限までに発注が要る」まで言い切る。
