# 入力データの仕様

`extract_data.py` は列位置を決め打ちせずヘッダ文字列から判定するので、通常はここを
読まなくても通る。判定に失敗したときだけ、この資料で構造を確認する。

## 会場ファイル（レジ通過単品売上）

各会場から届く物販日報。シート名は `レジ通過単品売上` 固定。会場ごとに列位置が違う。

### 自動判定のルール

| 項目 | 判定方法 |
|---|---|
| ヘッダ行 `hr` | 4列目が `商品名`、5列目が `JAN` の行 |
| 日付行 `dr` | `hr + 1` |
| 日次列 | ヘッダ行に `1, 2, 3, …` と連番が入っている列 |
| 税込単価 | 日付行が `(税込)` の列 |
| 販売数 | ヘッダ行が `販売数` の列 |
| 販売金額 | 販売数の隣の列 |
| 販売可能数 | ヘッダ行が `販売可能数` の列 |
| 理論上在庫 | ヘッダ行が `理論上` の列 |
| 納品合計数 | ヘッダ行が `納品` かつ 日付行が `合計数` の列 |
| 内覧会 | ヘッダ行が `内覧会` の列（東京のみ） |
| 入場者数 | ヘッダ行より上で `入場者数` ラベルがある行 |

日次列を「連番」で拾うのが肝。東京には日次列の手前に `内覧会`（12/4）の列があり、
日付だけで拾うとこれを会期1日目と誤認する。連番なら確実に会期分だけ取れる。

### 実績で確認した列位置（参考）

| 会場 | ヘッダ行 | 日次開始列 | 日数 | 販売数 | 販売可能数 |
|---|---|---|---|---|---|
| 東京（池袋） | 9 | 14 | 25 | 39 | 65 |
| 名古屋 | 6 | 11 | 19 | 32 | 48 |
| 博多 | 6 | 11 | 26 | 37 | 54 |
| 大阪（梅田） | 6 | 11 | 20 | 31 | 52 |
| 札幌 | 7 | 13 | 20 | 33 | 50 |

### 元データの既知の癖

- **内覧会**：東京の12/4分（全商品計142個）。会場間比較の公平性のため会期実績からは除外する。
- **小数の混入**：名古屋の販売可能数に小数を含む商品が3件ある（1389.6／2265.2／9.6）。
  `build_report.py` が整数に丸める。合計への影響は1個未満。
- **価格改定**：イメージリング8種は東京¥22,000→名古屋以降¥27,500。
  販売金額は必ず**各会場の実売単価**で計算する（⑤シートに会場別の単価列がある）。
- **報告書の総売上との差**：本レポートの物販売上はレジ袋代・音声ガイド・当日券を除いた
  商品売上（税込）なので、会場報告の総売上とは一致しないことがある。

## 在庫ファイル ★最重要の注意点

このファイルには**複数時点のスナップショットが同居している**。使うシートを間違えると
在庫判定が根本的に狂うので、必ず下記のとおり選ぶこと。

### 使うのは「在庫フロー台帳」だけ

シート `【清算(卸値67％)】池袋・名古屋_検品差異` が会場ごとの在庫フロー台帳。
1行が1商品で、会場ごとに次の並びが横に続く。

```
追加発注 → 理論在庫 → 販売数 → 理論在庫 → レッグス検品数量 → 実在庫
```

段階ラベル行（ヘッダ行の1つ上）に `池袋まで(SET)` `名古屋まで(SET)` `福岡まで(SET)`
`梅田まで(SET)` と入っている。**最後の段階の「実在庫」列が現時点の残在庫想定**で、
その会場の返送検品結果まで反映済み。2026/7/28時点では BB列（梅田まで(SET)）＝合計274,688個。

`extract_data.py` は「実在庫」で始まる列をすべて拾い、最後のものを採用したうえで、
どの列を使ったかを必ず表示する。会場が進んで列が増えても自動で最終列に追随する。

### 使ってはいけないシート

以下は**すべて同一の183,696個**で、池袋（東京）会場終了時点の古いスナップショット。
これを最新在庫として使うと、名古屋・博多・大阪の消費と返送、および追加生産
（累計で数十万個規模）がまったく反映されない。

| シート | 中身 |
|---|---|
| 元データ / CX01 / DB00 | 保管場所別の理論在庫（池袋終了時点） |
| 在庫合算 (2) | 上の合算 |
| 在庫元データ(12月清算後) | シート名どおり12月清算後 |
| 在庫合算(東京まで) | シート名どおり東京まで |

`◯.◯レッグス倉庫検品結果(◯◯返送分)` シートは各会場の返送良品で、これ単体では
在庫にならない（台帳の「レッグス検品数量」「実在庫」に既に織り込まれている）。

### 単位の罠：SET商品

ポストカードセット（5枚入・9枚入）と宿儺の指風お菓子は SET商品で、
`発注総数(SET数)` と `発注総数` の比がセット入数（5 / 9 / 10）。
台帳内で**列によって単位が混在する**（発注数・理論在庫はバラ、実在庫はSET＝販売単位）。
そのため在庫判定に使えるのは実在庫列だけ。発注総数から在庫を検算しようとすると必ず破綻する。

### 検算のしかた

フロー計算で在庫がマイナスになったら、まずスナップショットの日付を疑うこと。
実際にこの取り違えが起きており、池袋時点の在庫を7/8時点と誤認した結果、
宿儺の指風お菓子を13,826個（実際は460個）と30倍に過大評価していた。

## ロジ（倉庫WMS）の在庫データ

倉庫システムからの出力。シートは1枚、1行1商品で、ヘッダは1行目。

| 列 | 用途 |
|---|---|
| 商品ID | JAN。これで台帳・日報と突き合わせる |
| 在庫数(引当数を含む) | **倉庫の実棚残。これを倉庫残として採用する** |
| 引当数 / 入荷予定数 / 出荷予定数 | 引当・入出荷予定。0でないときは在庫の解釈に注意 |
| 最終入荷日 / 最終出荷日 | YYYYMMDD の数値。会場出荷が反映済みかの確認に使う |

`引当数` は `在庫数(引当数を含む)` に部分一致してしまうので、**完全一致で列を取る**こと。

### 台帳との突き合わせで分かっていること（2026/8/5データ）

- 42SKU中41件が収載。**宿儺の指風お菓子だけ載っていない**（食品のため別倉庫か）。
- 大半は台帳から計算した倉庫残（残在庫 − 会場納品）と ±数個で一致する。
- **ポストカードセット2種だけ大きく食い違う**（9枚入 ロジ2,715 vs 台帳計算26,711、
  5枚入 1,694 vs 5,690）。SET／バラの単位差が疑わしいが、5でも9でも割り切れない。
  ★要確認事項として毎回上げること。

## 運営からの欠品報告メール

`.msg` 形式で届く。本文は OLE の `__substg1.0_1000001F` ストリーム（UTF-16LE）。
`olefile` で読める。

```python
import olefile, re
f = olefile.OleFileIO('報告.msg')
for e in ('/'.join(x) for x in f.listdir()):
    if re.search(r'__substg1\.0_1000001F', e):
        print(f.openstream(e).read().decode('utf-16-le'))
```

読み取ったら `config.py` の `SHORTAGE` と `SHORTAGE_REPORT_DATE` を更新する。
「追納困難」等の但し書きも本文どおりに残す（実在庫と食い違うことがあり、
その齟齬自体が依頼者への報告価値になる）。
